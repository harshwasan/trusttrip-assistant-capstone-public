Using the exact feature and personas from Part 1 — not a new idea — build a genuinely working prototype, evaluate whether its outputs are trustworthy, and wire up an automation around it.
Tasks
1. Build and publish a working no-code AI app implementing the selected feature, using any one no-code AI app builder (Google AI Studio, Lovable, Replit, or Bolt). Before building, write the prompt you will use to generate the app using the six-part prompting structure — Capacity, Request, Insight, Specifics, Personalization, Examples — and include this prompt verbatim in your document. The published app must have: (a) basic user sign-in/authentication, (b) a persistent database (e.g. Firebase Firestore or an equivalent free database your builder provides) that stores each user's submitted trip preferences and the itinerary generated for them, and (c) a public, working link. Paste the public link into your document.
2. Classify the feature as AI-augmented or AI-native, with a one-paragraph justification tied to how much of the experience would stop functioning without the AI layer. State which stage of the 4D framework (Detect, Decide, Draft, Do) the feature primarily operates in, and which level of the AI Feature Ladder (L0–L4) it currently targets, with a one-line reason.
3. Design and document one automation built around your app using the Trigger / Logic / Action structure (and, if you use an agent-style tool, the fuller Goal / Trigger / Context / Model & Logic / Tools & Actions / Human Review structure). At minimum, the automation must: (a) trigger whenever your app generates a new itinerary, (b) call an LLM (via Groq's free tier, or your builder's own free-tier model) to produce a one-line "why this itinerary" explanation for the user, and (c) write a new linked record into a third Airtable table, Itinerary_Log (columns: Timestamp, Persona [a genuine Linked Record field pointing into Part 1's Personas table], Itinerary Summary, AI Explanation, Review Status), added to the same Airtable base as Part 1's Personas and Opportunity_Backlog tables — plus an explicit human-review checkpoint before that explanation is shown to the user (an unreviewed AI explanation shown directly to a real customer is a catastrophic, hard-to-reverse action, not a reversible one — so it must stay human-reviewed, never fully automated). Document this as a text node-by-node table (not a diagram), and paste a transcript of at least 3 real end-to-end test runs (your typed input → the automation's actual output, copied as text).
4. Run an Evals pass on your built app. Define at least 5 rubric-based criteria (e.g. Accuracy, Clarity, Completeness, Tone, Formatting, each rated on a 1–5 scale) and at least 5 assertion-based yes/no checks (e.g. "Does the itinerary respect the stated budget?", "Are all suggested dates within the stated travel window?") specific to a trip-itinerary output. Build a golden dataset of at least 8 diverse test inputs varying traveller type (solo/family/couple/group), destination (domestic/international), duration, and budget (state each budget in Indian Rupees). Run all 8 inputs through your actual built app and score every output against both your rubric and your assertions in a table.
5. Run a pre-launch Responsible-AI design pass. Cover, at minimum: (a) one concrete design choice that mitigates prompt injection in your app's input handling; (b) one concrete design choice that mitigates hallucination (e.g. requiring the app to only recommend from a fixed catalogue rather than inventing hotel names); (c) which specific PII fields your app collects and one Privacy-by-Design choice for each; and (d) for each of the four biases named in the MakeMyTrip recommendation-bias case study — popularity bias, price bias, geographical bias, and review bias — state one concrete design choice your prompt or ranking logic makes to reduce that specific bias in your own built prototype.
Acceptance criteria
- The app link loads, requires sign-in, and a fresh test submission is verifiably saved to the database (screenshots are not accepted — describe how you verified persistence, e.g. "logged in twice and confirmed the second session showed the first session's saved itinerary").
- The AI-augmented/AI-native classification is stated with a justification, and the 4D stage plus AI Feature Ladder level are each named with a one-line reason.
- The automation is documented as a text Trigger/Logic/Action (or full agent-architecture) table, includes the human-review checkpoint, writes a genuine linked Itinerary_Log record (with Persona as a real Linked Record field, not a retyped name), and the 3+ test-run transcript shows real input and real output text (not placeholder text).
- At least 5 rubric criteria and 5 assertion checks are defined, the golden dataset has 8+ inputs varying all four stated dimensions with budgets in Rupees, and all 8 are actually scored against both eval types in a results table.
- All four named MakeMyTrip biases (popularity, price, geographical, review) each have one concrete, feature-specific mitigation design choice — a generic "we will be fair" statement with no stated mechanism does not satisfy this — plus the prompt-injection, hallucination, and PII/Privacy-by-Design items are each concrete and specific to this app.
